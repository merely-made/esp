# Provider-bound embedding persistence

**Status (2026-10-20):** landed; resident receiving gate qualified. Retained contract:
`eidetic/design_docs/eidetic_docs/implementation_strategy/2026-10-11_eidetic_development_plan.md`,
P4 and the October 20 envelope continuation. Resident gate: Mere's
`2026-10-15_resident_inference_and_recall_plan.md`, I10. These own policy and the
cross-family acceptance; this document records ESP's API and implementation.

## Implementation and done-conditions

1. Providers report the exact algorithm/artifacts and transformations they
   actually loaded. Unknown providers refuse guarded persistence. Done when
   lexical configuration and loaded BERT buffers produce reproducible identities
   and changed settings/artifacts change that identity.
2. The optional persistence feature exposes a provider-bound index wrapper.
   Done when deserialized dense/sparse indexes validate shape, metric, finite
   values and sparse ordering, then match the complete expected envelope before
   search. Generic numerical APIs keep their existing independent use.
3. Qualification follows the resident consumer. Done when matching cold reopen,
   same-dimension foreign-space refusal and measured lexical/fused recall use
   this API with a real provider over exact retained sources.

## Findings

- 2026-10-20: `SemanticSearch::with_index` historically checks numerical
  dimensions, without embedding-space identity. `embed::compatible` adds the
  guarded path without changing the numerical API or the default feature cone.
- 2026-10-20: in-memory BERT component assembly cannot attest original loaded
  bytes. `from_bytes` and the persistence-enabled file loader bind exact config,
  tokenizer and safetensor buffers; manually assembled providers remain unknown.
- 2026-10-20: legacy numerical records have no envelope and cannot be silently
  promoted into a compatible persisted projection. Hosts can rebuild from their
  admitted sources; incompatible cached records return explicit refusal.
